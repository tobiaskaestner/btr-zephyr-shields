# L4-ADC — an ADC nexus on the Arduino R3 connector and both boards

**Status:** briefed 2026-08-14, ready to dispatch. Backlog item 35.
Unblocked: item 33 landed the model (`88e53fc`), item 34 landed 3-cell
PWM (`0373cd2`), and ADC needed no cell-count work at all.

This is the last piece that makes `grove_light` resolve through a grove
base carrier on a real twister platform — the payoff
`grove-carriers-brief.md` §5 describes and does not yet reach.

## 1. Scope

1. `dts/bindings/connectors/arduino-r3.yaml` gains `io-channel-map`,
   `io-channel-map-mask`, `io-channel-map-pass-thru` and
   `#io-channel-cells`, exactly as `dts/bindings/connectors/grove.yaml`
   already declares them. Copy that binding's shape; do not invent one.
2. `boards/extend/st/nucleo_f401re/arduino_r3_socket.dtsi` and
   `boards/extend/nxp/frdm_k64f/arduino_r3_socket.dtsi` each gain a real
   `io-channel-map` over their analog positions.
3. A corpus rig and a twister suite proving an ADC shield resolves
   through a carrier-exposed socket on a real board.

**PWM is NOT in this slice** — that is item 36, deliberately sequenced
after this one. Do not add `pwm-map` anywhere.

## 2. THE DOMINANT COST — read this first

Adding a property to a board's socket node changes that board's
devicetree, and **`zephyr.dts` goldens contain the whole board**. Every
accept rig on these two boards moves its `zephyr.dts` golden:
`nucleo_datalogger`, `nucleo_wifi_logger_ok`, `nucleo_mux_farm`,
`pilot_variants`, `shield_rev_pilot`, `shield_rev_family`,
`ard_datalogger`, `nucleo_grove_farm` (nucleo) and `frdm_eth_nest`
(k64f) — re-derive the list, do not trust it.

**`RIGC_REFREEZE=1` is BLOCKED by the harness classifier**, so these must
be regenerated by hand. The workable method is the one the
`nucleo_grove_farm` slice used: run `rigc expand` / `west build-rig
--cmake-only` directly, apply the harness's own `normalize()` and
`normalize_dts_provenance()` from
`scripts/rigc/tests/integration/conftest.py`, and write the result.
**Run under pytest's DEFAULT basetemp** — a custom `--basetemp` breaks
`normalize_dts_provenance`'s regex and leaves absolute scratch paths in
the provenance comments, which `dts_equiv` would not catch because it
ignores comments. Grep each regenerated golden for `pytest-of` and for
your own scratch path before believing it.

**The diff review IS the deliverable here.** For every moved golden,
show that the ONLY change is the ADC nexus addition. A golden that moved
for any other reason is a finding you must report, not noise to absorb.

## 3. The board facts

**Verified by reading upstream** (`zephyr/boards/st/nucleo_f401re/arduino_r3_connector.dtsi`
and `zephyr/boards/nxp/frdm_k64f/frdm_k64f.dts`) — these pin assignments
are facts, not predictions:

| position | nucleo_f401re | frdm_k64f |
|---|---|---|
| A0 | PA0 | PTB2 |
| A1 | PA1 | PTB3 |
| A2 | PA4 | PTB10 |
| A3 | PB0 | PTB11 |
| A4 | PC1 | PTC11 |
| A5 | PC0 | PTC10 |

**NOT verified, and this is the slice's real research**: which ADC
controller and which channel number each pin is. Derive them from the
SoC's own sources (the STM32 HAL pinctrl definitions for
`adc1_in<N>_p<x><n>`; the Kinetis `ADC<n>_SE<m>_PT<x><n>` pinmux macros),
never from this table and never from memory. `nucleo_f401re.dts` already
uses `&adc1` with `pinctrl-0 = <&adc1_in0_pa0>`, which tells you the
naming convention and confirms A0 is `adc1` channel 0.

**Expect k64f to need TWO parents.** Its analog pins look likely to split
across `&adc0` and `&adc1`. That is fine — each `io-channel-map` row
carries its own phandle, and `rigc/board_edt.py::_project_channel_map`
reads `entry.parent` per entry. **Confirm rigc actually handles a
multi-parent ADC map by test**, since nothing in the tree exercises one
today; if it does not, that is the finding and this slice stops to
report it.

**Declare only the positions you can source.** A socket exposes the
subset it actually wires, declared by absence — the same rule
`arduino_r3_socket.dtsi` already applies to `socket,uart`. Do not invent
a channel to fill a table.

## 4. Pin-mux is board-provided and stays stubbed

rigc already treats pin-mux as the board's business and emits a
config-sheet note saying so; upstream's `adc0_default`/`adc1_default`
pinctrl groups declare unrelated channels. **Do not author pinctrl
groups for the analog pins.** A `--build-only` twister run does not need
them, and inventing them is board work with no upstream fact behind it —
the same reasoning that kept a NanoC6 `pwm-map` out of the
`grove_pwm_led` slice. Note the limitation in the rig's own comment so a
reader is not left to wonder whether it would work on hardware.

## 5. The witness

An ADC shield through a carrier-exposed socket, on a real board:
`grove_light` on a `seeed_grove_base_v2` carrier's `grove_a0`, on
`nucleo_f401re`. Either extend `nucleo_grove_farm` or add a sibling rig —
extending it is cheaper (its golden is moving anyway, §2) but changes an
existing rig's meaning; adding one costs a fresh golden set. **Pick one,
say which and why.**

Plus a twister suite, `--build-only`, on both platforms if both end up
with an ADC nexus. `tests/rigs/nucleo_grove_farm/` is the pattern.

Note the modelling wrinkle, and do not try to fix it here: the grove
carrier's `grove_i2c` maps SIG0/SIG1 to A5/A4, the classic Arduino I²C
location, but on these boards I²C is on D14/D15 and A4/A5 are plain
analog pins. The `socket,i2c` pass-through resolves by KIND, not by pin,
so it works — but a reader comparing the two will notice. Out of scope.

1. `arduino-r3.yaml` declares the ADC nexus properties, shaped like
   `grove.yaml`'s.
2. Both board sockets declare a real `io-channel-map`; every channel
   number sourced from the SoC's own definitions, and the source named
   in the report.
3. `grove_light` resolves through a carrier-exposed `grove_a0` on
   `nucleo_f401re`, proven by an emitted overlay containing resolved
   `io-channels` and `&adc… { status = "okay"; };`.
4. A twister suite building clean (`--build-only`), run and reported.
5. Multi-parent ADC map confirmed working, or reported as broken (§3).
6. **Every moved golden accounted for**: the list, and for each, evidence
   that only the ADC nexus changed. No golden moved for an unexplained
   reason. No `pytest-of` or scratch path in any regenerated file (§2).
7. No `pwm-map` anywhere — that is item 36.
8. Full gate green, driver-run. Last driver-verified: mypy clean, unit
   **755**, integration **282**, coverage **93%** (2026-08-14, `0373cd2`).
   Re-derive rather than carry.
